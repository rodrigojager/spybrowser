# Reproducible local motion-quality benchmark

From the repository root, run this single command in a **fresh `dotnet` process**:

```powershell
dotnet run --project tools/native-motion-benchmark/NativeMotion.Benchmark.csproj -c Release
```

It writes `artifacts/motion-quality/motion-quality.json` (complete machine-readable results) and `motion-quality.md` (short interpretation). Use an optional first argument to choose another output directory. Metadata captures exact `git rev-parse HEAD` and the complete `git status --porcelain=v1 --untracked-files=all` output before measurement, plus seed and dataset hash. The first generator invocation is the cold dataset load + Cursory generation in that fresh process. Warm Cursory generation p50/p95 and current-thread managed allocation are measured separately from browser dispatch. The benchmark validates exactly 14 real DOM page runs (2 algorithms × 5 cases, with 3 pages in each concurrent-pages case). The benchmark does not impose a 10 ms pass/fail threshold; the plan's p95 <10 ms budget is an investigation target for a documented reference machine, not a shared-runner assertion.

The executable compares the existing Bézier baseline and native Cursory on the same local case definitions, seed (`21021`), start/end coordinates, headless Playwright Chromium settings, and configured 300 ms movement budget. Every case gets a fresh independent page; three pages run concurrently in the final case. Cursor positions are explicitly initialized on each real page before measurement. The cases cover short/subpixel, long, stable-button activation, deliberate slow transport, and concurrent independent pages. The button case verifies actual DOM hover and one click activation for both algorithms.

For each page the JSON reports planned and observed wall duration, observed DOM `mousemove` count, chronological ordering, path length and endpoint displacement in pixels, interval distribution in milliseconds, velocity distribution in px/s, acceleration magnitude derived from adjacent segment-velocity changes divided by mean adjacent interval in seconds (px/s²), pauses >=50ms, and completion. Zero-duration segments use zero velocity/acceleration; empty metric series report finite zero summaries. `performance.now()` is measured in the page; these timings are observations with OS/browser scheduling tolerance, not bit-for-bit reproducible promises. Planned time is the configured duration budget; Cursory is scaled to it and Bézier's duration is clamped to it. The configured minimum and maximum are identical for the benchmark.

The slow case inserts an explicitly acknowledged artificial 12 ms delay in a delegating `IPage`/`IMouse` adapter immediately before each real `IMouse.MoveAsync`. It is a real Chromium DOM movement with additional adapter latency, **not** CDP or network latency. JSON records the case label. Memory reporting includes benchmark-process working-set delta, an aggregate managed-allocation delta for the browser phase, and Chromium `performance.memory.usedJSHeapSize` before/after per page when exposed (otherwise null). These are snapshots, not peak or exclusive ownership; no browser-child-process attribution is claimed. The run validates that every page completed, DOM timestamps remained chronological, and every serialized numeric metric is finite before writing the artifacts.

The JSON records CPU identifier when Windows provides it, logical processors, OS, process architecture, .NET runtime and SDK, Playwright and browser versions, source revision and dirty state, seed and SHA-256 of the exact embedded gzip dataset. Interpret results in three classes: (1) functional correctness—completion, chronological DOM observations and finite metrics; (2) performance—cold/warm generation, allocation and dispatch/rhythm measurements, descriptive rather than gated; (3) regression—only a paired same-context comparison can establish a regression, otherwise report a contextual difference. Compare OS/runtime/browser, dataset, seed, concurrency, source revision and dirty state before attributing changes. The Bezier/Cursory same-run tasks compare algorithms but do not constitute a historical baseline-vs-candidate package-consumer proof against e217359. Browser-dispatch timing is reported separately from generator-only cold/warm data; total elapsed action is not presented as pure algorithm cost. Repeat on the same recorded reference hardware and browser for a meaningful comparison. Differences are functional/performance/observed-rhythm evidence only; there is no claim of improved humanness, stealth, CAPTCHA results, or detection avoidance, and no human movement recordings are collected. Dataset redistribution and external distribution remain BLOCKED pending independent review; benchmark execution is not legal clearance.

## Historical package-consumer comparison (ticket 21)

`tools/historical-motion-comparison/run.py` archives and builds the approved historical source `e217359d19a29635f2b3b5ba54664d299fd16d36` separately from the candidate; it never adds a project reference from the consumer. Each feed has a versioned Core/Playwright package set (plus Cursory only in the candidate), a manifest binding the exact source commit and canonical git tree SHA to every nupkg SHA-256, and an isolated `NUGET_PACKAGES` cache. The producer's raw git-archive SHA is also recorded; tar bytes differ between Windows and Linux, so consumers verify the canonical source tree SHA (and package nuspec commit) rather than comparing host-specific tar hashes. NuGet source mapping permits SpyBrowser IDs only from that local feed; all external dependencies come from NuGet.org. Consumer assets are inspected to verify the expected package version and absence of SpyBrowser project references. Candidate Bezier, candidate Cursory, candidate raw/off, and historical Bezier are run against the same loopback DOM matrix (short/subpixel, long, stable hover/click, 12 ms per-move dispatch latency, and three independent pages), with the same viewport, endpoints and movement-duration settings.

For the preliminary harness verification at the assigned revision `d79c085ca4f6e349ad5b0ed744158653ee6382b6`, run from the repository root:

```powershell
python tools/historical-motion-comparison/run.py --build-preliminary-candidate --output artifacts/historical-motion-comparison/preliminary
```

This creates an explicitly preliminary candidate feed, not parent-final package evidence. After the parent provides its final candidate feed, rerun with that feed, preserving its manifest and package hashes:

```powershell
python tools/historical-motion-comparison/run.py --candidate-feed <final-feed-directory> --output artifacts/historical-motion-comparison/final
```

The runner rejects feed package hash mismatches, source tree/source revision mismatches, package nuspec commit/version mismatches, undeclared nupkgs, and SpyBrowser project references in consumer assets. It reports actual package source/version, source/archive/tree hashes, feed-manifest hash and (when present) embedded dataset hash in each result. Historical Bezier exposes no supported seed control; the requested seed is recorded, but the report explicitly says it is not used there. Do not call the resulting tasks a paired trajectory or bit-reproducible timing comparison. Functional completion, observed rhythm and operational cost are distinct; a regression claim requires repeated paired runs under matched environment/browser conditions. No CAPTCHA, stealth, detection-avoidance or human-recording conclusion is made.
